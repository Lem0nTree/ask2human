# t2000 mainnet payments

The marketplace payment path uses `@t2000/sdk` **11.7.0** against Sui
mainnet. It creates the SDK's native USDC job object and does not publish or
call a project Move package. The canonical money tuple is:

| Field | Value |
| --- | --- |
| `asset` | `USDC` |
| `network` | `mainnet` |
| `decimals` | `6` |
| `coinType` | `0xdba34672e30cb065b1f93e3ab55318768fd6fef66c15942c9f7cb846e2f900e7::usdc::USDC` |

New API amounts are unsigned decimal strings in atomic USDC units. Task
creation uses `amountAtomic`, `maxTaskAtomic`, and `totalBudgetAtomic`; budget
read models additionally return `reservedAtomic`, `spentAtomic`, and
`availableAtomic`. Migration `003_t2000.sql` renames the old physical
`*_mist` columns to `*_atomic`. Existing rows retain their integer values and
are tagged `SUI`/`testnet`/`9` with `legacyReadOnly=true`; payment actions reject
those rows.

The server defaults missing task terms to a five minute review window and a
`rejectSplitBps` of `5000` (a 50% buyer share on rejection). The terms are
copied into the approval, frozen job transaction, and settlement record.
`rejectSplitBps` is the buyer share used by the t2000 escrow contract:
`buyerRefund = floor(total * rejectSplitBps / 10000)` and
`sellerGross = total - buyerRefund`. For example, a worker share of 25% uses
`rejectSplitBps=7500`. Rejection accounting applies the actual t2000 fee to
that seller gross amount. Funding returns a current protocol fee quote before
signing, while terminal settlement records the fee and net observed on the
finalized Job.

Every build action resolves object references and gas once, stores the exact
transaction bytes and digest, and returns the same bytes on retry:

```json
{
  "taskId": "…",
  "transactionBytesBase64": "…",
  "expectedDigest": "…",
  "asset": "USDC",
  "network": "mainnet",
  "decimals": 6,
  "state": "FUNDING",
  "amountAtomic": "100000",
  "terms": { "reviewWindowMs": 300000, "rejectSplitBps": 5000 }
}
```

The browser signs these bytes and confirms only the returned digest. The
server waits for finality, checks the sender, package, USDC Job type, buyer,
seller, amount, brief hash, deadline, review terms, state, and delivery hash,
then updates PostgreSQL. A receipt that fails any check is rejected without
moving the task to its next state.

The exported server actions are:

- `buildFundingTransaction` / `confirmFunding`
- `acknowledgeFundingFee`
- `buildScoreSetupTransaction` / `confirmScoreSetup`
- `buildSubmissionTransaction` / `confirmSubmission`
- `buildReleaseTransaction` / `confirmRelease`
- `buildTimeoutClaimTransaction` / `confirmTimeoutClaim`
- `buildRefundTransaction` / `confirmRefund`
- `buildRejectTransaction` / `confirmReject`
- `buildRatingTransaction` / `confirmRating`
- `getTaskRating`

The timeout claim uses the worker wallet after the on-chain delivery review
window has elapsed and does not require a new owner approval. Owner release,
refund, rejection, and rating still require their corresponding authenticated
server checks. `accept_task` is retained as a compatibility export that fails
closed; applications and explicit worker selection assign a worker first.

Funding recovery is single-attempt. Expired pending or approved HIRE approvals
are marked expired and a fresh HIRE may be requested only while the task is
`ASSIGNED`. Once bytes are issued, the task remains `FUNDING` and the same
frozen bytes and digest are returned for resumption until confirmation or the
task deadline; owner authentication cannot authorize a second funding attempt.
If an issued approval is missing its frozen bytes, recovery fails closed for
manual reconciliation. Anonymous `/api/state` open-task records omit `brief`
and `rubric`; the private fields are returned only to the owner, selected
worker, or verified wallet-linked worker in the matching category.

Settled payment responses and read models use this shape:

```json
{
  "amountAtomic": "1000000",
  "grossAtomic": "1000000",
  "feeAtomic": "25000",
  "netAtomic": "975000",
  "feeBps": 250,
  "asset": "USDC",
  "network": "mainnet",
  "decimals": 6,
  "coinType": "…::usdc::USDC",
  "packageId": "…",
  "jobId": "…",
  "scoreReadyAt": null,
  "scoreReady": false,
  "deliveredAt": "2026-09-26T00:00:00.000Z",
  "settledAt": "2026-09-26T00:00:00.000Z",
  "fundingDigest": "…",
  "submissionDigest": "…",
  "releaseDigest": "…",
  "refundDigest": null,
  "rejectionDigest": null,
  "reviewWindowMs": 300000,
  "rejectSplitBps": 5000,
  "status": "PAID"
}
```

The t2000 Job states are `funded`, `delivered`, `released`, `refunded`, and
`rejected`; application states are `FUNDING`, `FUNDED`, `SUBMITTED`, `REVIEW`,
`PAID`, `REFUNDED`, and `REJECTED`. A score object is required by the SDK for
delivery and terminal settlement. Ratings are private while pending and gain
`ratings.confirmed_at` only after the finalized rating receipt passes all
checks; public profile aggregates must filter on that field.

`confirmFunding` returns the quoted and observed fee fields. If the finalized
funding receipt reports a different fee, the worker must call
`acknowledgeFundingFee(session, taskId)` before a submission can be built;
the action is idempotent and returns the updated settlement DTO. The
settlement `feeAtomic` is the protocol fee deducted from the seller gross, so
`feeAtomic + netAtomic` is the seller payout gross for both `PAID` and
`REJECTED`; `grossAtomic` remains the full escrow amount. A `REFUNDED`
settlement is excluded from seller earnings.

The `score_id` column stores the on-chain score object ID. The `score_digest`
column stores the finalized score setup transaction digest and is never used
as a Move score object argument. `score_ready_at` is the authoritative
readiness marker: it is populated only after a score receipt is validated or
an existing score object is read successfully. A deterministic `score_id`
stored while setup is frozen does not imply readiness, so clients must use
`scoreReadyAt` (and a confirmed historical score where applicable), not the
ID alone. If a worker score setup is already frozen,
refund recovery keeps it intact and stores a separate owner-sponsored score
attempt in `refund_score_*` columns. If an owner needs to refund before a
worker score exists, `buildRefundTransaction` first returns that owner-signed
transaction (`state: SCORE_FUNDING`); after `confirmRefund` validates it (or
reconciles a score race), call the build action again for the refund.

Settlements and task read models expose `deliveredAt` from the finalized
on-chain delivery transaction. Review countdowns must use that chain timestamp
rather than the local submission confirmation time. The settlement DTO also
includes `feeQuoteBps`, `feeQuoteAtomic`, `fundingFeeBps`,
`feeAcknowledgedAt`, and `feeChanged` when applicable.

## Bounded trial

`npm run t2000:trial` loads `.env` if present and performs a dry run. It does
not build, sign, or broadcast a transaction. The execute path is explicit:

```sh
npm run t2000:trial -- --execute
# Optional amount, still hard-capped at 0.10 USDC:
npm run t2000:trial -- --execute --amount-atomic=100000
```

The main integration thread must hold the trial lock before the process reads
the checkpoint or signs anything. For the first bounded execution, use:

```sh
flock -n /tmp/ask2human-t2000-trial.lock -- npm run t2000:trial -- --execute --amount-atomic=20000
```

The script requires `SUI_NETWORK=mainnet`, canonical t2000 configuration, and
the private wallet variables `OWNER_WALLET_PRIVATE` and
`WORKER_WALLET_PRIVATE`; matching public variables are checked when present.
It runs one small funded → delivered → released job, creates the worker score
if necessary, and may transfer a bounded SUI gas top-up to the worker. It
never prints private keys, transaction bytes, signatures, or database URLs.

The cumulative spend file defaults to `/tmp/ask2human/t2000-trial-spend.json`
and records only safe totals plus resumable stage metadata and frozen
transaction checkpoints. Its mode-0600 checkpoint includes the exact frozen
transaction bytes needed for recovery, never private keys or signatures. A failed run resumes the exact frozen bytes and digest. Use
`--new-run` only after a prior run reaches `done`; it carries forward the
durable cumulative totals and never starts a second funding job after an
unresolved stage. Before any top-up or signing, the trial preflights the full
lifecycle balance requirements and reserves its caps. Across invocations it
caps task funding at
`100000` USDC atomic units (`0.10` USDC) and reserved gas/transfers at
`50000000` MIST (`0.05` SUI`). Review and execute this trial only from the
main integration thread after the deployment and wallet checks are complete.

The adapter and SDK references are the [official t2000 Agent SDK guide](https://docs.t2000.ai/agent-sdk),
the [job builders](https://github.com/mission69b/t2000/blob/main/packages/sdk/src/wallet/job.ts),
and the [reputation builders](https://github.com/mission69b/t2000/blob/main/packages/sdk/src/wallet/reputation.ts).

## Dependency audit qualification

The lockfile pins `@t2000/sdk` **11.7.0**. Its transitive
`@mysten/zklogin` **0.8.1** dependency is deprecated and brings a nested
`@mysten/sui` **1.16.1** dependency with `valibot` **0.36.0**, which is flagged
by the current dependency audit with high-severity advisories. This application
uses the SDK's regular Job/payment APIs; it does not use the SDK's zkLogin
surface. The transitive `@phala/dcap-qvl` **0.5.3** → `elliptic` **6.6.1**
path is also reported with a low-severity advisory and is not imported by
application source. This is a qualified audit state, not a clean audit claim.
Do not force a t2000 SDK downgrade or add cross-major dependency overrides to
silence these findings; track the upstream dependency updates and re-evaluate
the lockfile when they are available.
