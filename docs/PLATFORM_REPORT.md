# ask2human platform report

**Status date:** 26 September 2026
**Public app:** [ask2human.me](https://ask2human.me)
**Requirements:** [original product specification](../Agent_to_Human_Marketplace_Product_Spec.md) and [revised MVP plan](HACKATHON_COMPLETION_PLAN.md)

## Current assessment

ask2human is deployed on Vercel with Neon PostgreSQL and uses the existing t2000 escrow on Sui mainnet for real USDC. The deployment is public, but the application journey is only partly accepted; this report does not describe the platform as production-ready.

An independently checked t2000 SDK trial and a separate deployed application journey both completed mainnet payment. The deployed journey used the scoped agent API, separate World sandbox owner/worker sessions, exact fresh HIRE and RELEASE approvals, worker application/selection, private evidence upload/delivery, and payment followed by a confirmed five-star onchain rating. For the application task, independent checks matched **20,000 atomic USDC (0.02 USDC) gross**, **1,000 fee**, and **19,000 atomic USDC (0.019 USDC) worker net**. The dashboard shows zero pending escrow; owner accounting shows 20,000 spent and zero reserved. Repeated release/rating confirmation did not sign or broadcast another transaction.

[Completed task](https://ask2human.me/tasks/35dc7c07-3a92-4374-be37-d404aedbfbe7) · [Worker profile](https://ask2human.me/workers/a17b1a5f-f5b7-4b74-884f-87bdbbadd2f4). The release initially exposed three missing database fields; corrective migration 005 and an independent fresh-schema regression fixed this before the payment was signed.

The app uses real mainnet money alongside **World staging/sandbox identity**. That identity check establishes uniqueness in the configured demo environment; it is not production Proof of Human, legal identity verification, or proof that work was completed. The Slush connection modal and mobile deep link rendered in Chromium, but an actual Slush OAuth connection, wallet-binding signature, wallet transaction signing, cancellation and reconnect sequence remain unverified. Injected deployed `access_denied`, callback replay/missing-session and wrong-role fund/release/submit requests were rejected as expected; actual provider-UI cancellation remains unchecked; expired approval rejection passed.

Status labels below distinguish code from observation: **Verified** means the named deployed or chain behavior was observed; **Implemented** means the path exists in this repository but the corresponding external flow has not passed; **Pending** means the live check is in progress and has no result claimed; **Missing/deferred** means the feature is not in this delivery scope or is absent.

## Revised-plan product surfaces

- **Task pages and applications:** shareable detail pages, owner/worker next actions and explicit applicant selection are implemented; the deployed API create/apply/select path passed. See [task route](../app/tasks/%5Bid%5D/page.tsx), [experience service](../app/lib/server/experience.ts), and [agent example](../scripts/agent-example.ts).
- **Delivery and recovery:** private image/report upload, preview, frozen-byte retry and confirmation recovery are implemented. Deployed upload, authorized reads, anonymous denial and delivery passed; funding and delivery signatures came from a controlled local test harness, not a Vercel wallet. A cancelled Slush request and reconnect recovery have not been live-tested.
- **Earnings and profiles:** dashboard totals are based on confirmed settlement seller net, not a capped task feed or wallet balance. Pending escrow remains separate. Public profiles show only confirmed ratings and public task summaries; private briefs and evidence are excluded. Deployed rating, release confirmation, earnings and public recent-work views passed.
- **Agent operation:** scoped create/list/select/get/review/settlement commands and the example script are implemented. Deployed task creation, application, selection, delivery review and release request all passed.
- **Wallet:** the dApp Kit connection modal and mobile “Open in Slush” link render in Chromium. Slush-specific OAuth, wallet binding signatures, frozen transaction signing, user cancellation and reconnection are still unverified. The deployed funding and delivery actions were signed by a controlled local harness using supplied owner/worker keys; those keys were never configured in Vercel.

## Items not yet accepted or not included

These are distinct states rather than a general claim that the platform is incomplete:

**Implemented, live acceptance pending:** Slush OAuth/sign/reconnect, actual provider-UI cancellation and the full browser-wallet recording. Injected `access_denied`, callback replay/missing-session, actual expired approval and wrong-role payment denial checks passed. Core payment, rating, refund, timeout claim, rejection and dashboard/profile accounting passed independent acceptance. Final mainnet trial totals: 0.07 USDC funded and 0.060968632 SUI gas plus conservatively counted worker funding; see [proof of testing](PROOF_OF_TESTING.md).

**Missing or deferred against the original spec:** worker availability/schedule; draft and separate publish workflow; semantic prohibited/ambiguous-task screening; availability-aware worker search; broader policy administration such as editing limits and credential lifecycle. The current owner form publishes a task directly under its agent's budget/category policy. The revised plan defers MCP transport, chat, bidding, notifications, maps, advanced charts, a withdrawal system and a custom escrow implementation.

**Known security/operations limitation:** the dependency audit still reports upstream/transitive high-severity `valibot` and low-severity `elliptic` findings. The current application does not invoke the affected SDK zkLogin paths; no SDK override has been attempted. This report does not assert that the remaining dependency risk is resolved or that an independent production security audit has passed.

The historical custom Move escrow/testnet notes do not describe the deployed service. Current payments use the pinned t2000 mainnet integration. Real mainnet funds and sandbox identity coexist in this demo and must remain clearly labeled in product copy and recordings.
